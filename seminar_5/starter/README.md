## 1. Новый инструмент `compare_periods`

**Сигнатура:**
```python
def compare_periods(
    metric: str,               # "key_rate" | "fx_USD" | "fx_EUR" | "fx_CNY" | "cpi" | "unemployment"
    period_a: str,             # "YYYY-MM-DD" или "YYYY-MM"
    period_b: str,
) -> dict:
```

**Реализация:** Функция диспатчит по `metric` к существующим функциям (`get_fx_rate`, `get_key_rate`, `get_inflation`, `get_unemployment`), извлекает числовое значение из результата и считает `delta` (разность) и `ratio` (отношение).

**Примеры запросов:**

1. `"Во сколько раз вырос курс USD с января 2022 по апрель 2026?"` → compare_periods(fx_USD, 2022-01-01, 2026-04-30) → ratio=1.008 (вырос в 1.008 раза)
2. `"Как изменилась ключевая ставка ЦБ с 2022-01-01 по 2026-04-01?"` → compare_periods(key_rate, 2022-01-01, 2026-04-01) → delta=+7.5 п.п., ratio=1.88
3. `"Сравни инфляцию за январь 2023 и январь 2024"` — потенциальный запрос, требует compare_periods(cpi, 2023-01, 2024-01)

## 3. Диагностика трёх ошибок

### Ошибка 1: Галлюцинация — ответ без вызова инструмента

**Тип:** Агент не вызвал инструмент (пропустил шаг)

**Трасса (Q7):**
```
run_id: 1b7f62f66989435d863e8b0cb2c44c75
step 1 — финал-текст
→ "В году всего 12 месяцев, поэтому 13-го месяца в 2023 году не существует."
```

**Причина:** Модель решила, что раз месяц 13 невалиден, то и вызывать `get_inflation` не нужно — она ответила из общего знания. Это нарушение правила "числа получай только через инструменты". В системном промпте нет явного указания "всегда вызывай инструмент, даже если знаешь ответ".

**Что исправить:** Добавить в системный промпт правило: "Если вопрос подразумевает вызов инструмента — всегда вызывай его, даже если ошибочные аргументы. Не отвечай по памяти."

---

### Ошибка 2: Избыточные вызовы при отсутствии данных

**Тип:** Лишние вызовы (неэффективность)

**Трасса (Q3, run_id d80eb197...):**
```
step 1 → get_inflation(2026, 5) → {"error": "нет данных ИПЦ на 2026-05"}
step 2 → get_inflation(2026, 4) → {"error": "нет данных ИПЦ на 2026-04"}
step 3 → get_inflation(2026, 3) → {"cpi_yoy": 6.8}  ✓
       → get_inflation(2026, 2) → {"cpi_yoy": 7.0}  (лишний, не использован)
       → get_inflation(2026, 1) → {"cpi_yoy": 7.25} (лишний, не использован)
```

**Причина:** Агент не имеет информации о том, за какие месяцы доступны данные. Он перебирает месяцы подряд, пока не найдёт данные. На шаге 3 он вызвал 3 инструмента одновременно, но использовал только первый результат.

**Что исправить:** Добавить в описание `get_inflation` подсказку "последние доступные данные — март 2026" или реализовать инструмент `get_latest_available()`.

---

### Ошибка 3: Некорректная дата при работе с compare_periods

**Тип:** Неправильный порядок вызовов / неточная дата

**Трасса (Q5, run_id 62825843...):**
```
step 1 → compare_periods(fx_USD, 2022-01-01, 2026-04-30)
         → a: 74.2926 (2022-01-01), b: 74.8806 (2026-04-30)
         → ratio: 1.008
```

**Проблема:** Вопрос: "Во сколько раз вырос курс USD с января 2022 по апрель 2026?" Агент корректно взял `2022-01-01` как начало января, но для "апрель 2026" взял `2026-04-30` (конец апреля), а не начало апреля (`2026-04-01`). Разница небольшая (74.88 vs ~81.25 на 01.04), но подход неконсистентен: если начало периода — первое число, то и конец периода логичнее брать первым числом.

Также в отдельном ручном запуске с тем же вопросом агент взял `2026-04-01` и получил ratio=1.09 — результат отличается на 8%.

**Причина:** Описание `compare_periods` не уточняет, как интерпретировать "YYYY-MM" (начало или конец месяца). Агент сам выбирает.

**Что исправить:** Уточнить в описании `compare_periods` и `period_a`/`period_b`: "Для формата YYYY-MM период интерпретируется как первое число месяца, если не указан день."

## 4. Вывод: самый хрупкий элемент системы

На мой взгляд, **самый хрупкий элемент — это системный промпт**. 

Он выполняет сразу несколько функций:
1. Описывает правила работы (не придумывать числа, использовать calculate)
2. Перечисляет инструменты
3. Даёт алгоритмы (реальная ставка, индекс нищеты, кросс-курс)
4. Управляет форматом ответа

Любая неточность в промпте приводит к Observable-ошибкам:

- Если не сказать "всегда вызывай инструмент" — модель отвечает из памяти (ошибка 1)
- Если не описать формат дат — агент выбирает произвольно (ошибка 3)
- Если не указать порядок поиска данных — агент перебирает месяцы (ошибка 2)

Второй по хрупкости — **JSON-схемы инструментов**. Слишком краткое описание `calculate` заставляет агента считать вручную (и ошибаться). Плохо сформулированное описание `compare_periods` приводит к неверным аргументам. 

Третье — **fallback-механизм** (CSV вместо живого API). Он спасает, когда ЦБ недоступен, но данные могут устареть. Например, ключевая ставка 16.0% действительна с 20 марта 2026 — если ЦБ изменил ставку после этой даты, агент выдаст неверный ответ без явного указания на это (он говорит "данные из архива", но пользователь может не понять степень устаревания).
